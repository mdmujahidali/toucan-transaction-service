# Transaction Service — Toucan Engineering Challenge

## 1. Understanding of the problem

Build a small service that lets a client create a transaction, look one
up by ID, change its status, and list all transactions for a customer —
with input rejected up front when it's invalid, and duplicate
transaction IDs rejected outright.

## 2. Assumptions

**No variant email was received for this candidate**, so the following
defaults were used in place of an assigned variant. They are isolated to
a few files and can be swapped out easily if a real variant surfaces
later:

| Rule | Default used | Where it lives |
|---|---|---|
| Permitted currencies | USD, EUR, GBP, INR | `model/Currency.java` |
| Permitted transaction types | DEPOSIT, WITHDRAWAL, TRANSFER, PAYMENT | `model/TransactionType.java` |
| Maximum transaction amount | 1,000,000 | `dto/CreateTransactionRequest.java` |
| Minimum transaction amount | greater than 0 | `dto/CreateTransactionRequest.java` |
| Decimal precision | up to 2 decimal places | `dto/CreateTransactionRequest.java` |

Other assumptions:

- The **transaction ID is supplied by the client**, not generated by the
  server. This is implied by the requirement to "reject a Transaction ID
  that already exists" — that check only makes sense if the caller
  chooses the ID.
- A new transaction always starts in status **PENDING**. The create
  request does not accept a status field, so a transaction can't be
  created already "COMPLETED" without ever having been processed.
- `customerId` is a plain non-blank string, not validated against a
  separate customer database (none was provided).

## 3. Validation rules

Enforced via Bean Validation on `CreateTransactionRequest`:

- `transactionId` — required, non-blank.
- `customerId` — required, non-blank.
- `amount` — required, > 0, ≤ 1,000,000, at most 2 decimal places.
- `currency` — required, must be one of USD / EUR / GBP / INR.
- `type` — required, must be one of DEPOSIT / WITHDRAWAL / TRANSFER / PAYMENT.

An invalid `currency` or `type` value (something outside the enum) is
rejected before it even reaches the service layer, because Jackson fails
to deserialize it — the global exception handler turns that into a 400
with a clear message rather than a raw stack trace.

Business validation (in `TransactionService`):

- **Duplicate transaction ID** → rejected with `409 Conflict`.
- **Transaction not found** (get, or update-status on a missing ID) →
  `404 Not Found`.
- **Invalid status transition** → `409 Conflict`.

## 4. Status transition rules

| From | Allowed to |
|---|---|
| PENDING | COMPLETED, FAILED, CANCELLED |
| COMPLETED | *(none — terminal)* |
| FAILED | *(none — terminal)* |
| CANCELLED | *(none — terminal)* |

**Reasoning:** PENDING is the only non-terminal state — it exists
specifically to represent "not yet decided." Once a transaction has
actually completed, failed, or been cancelled, allowing further status
changes would let someone silently rewrite what actually happened (e.g.
flipping a FAILED payment to COMPLETED after the fact, without it ever
being reprocessed). If a transaction genuinely needs reversing, the
correct model is a new transaction (e.g. a refund), not mutating the old
one's status.

## 5. API endpoints

| Operation | Method & Path | Success | Failure |
|---|---|---|---|
| Create transaction | `POST /api/transactions` | `201 Created` | `400` invalid body, `409` duplicate ID |
| Get transaction | `GET /api/transactions/{transactionId}` | `200 OK` | `404` not found |
| Update status | `PATCH /api/transactions/{transactionId}/status` | `200 OK` | `404` not found, `409` invalid transition |
| Get customer transactions | `GET /api/customers/{customerId}/transactions` | `200 OK` (possibly empty list) | — |

Example create request:

```json
POST /api/transactions
{
  "transactionId": "TXN-1001",
  "customerId": "CUST-1",
  "amount": 100.00,
  "currency": "USD",
  "type": "PAYMENT"
}
```

Example update-status request:

```json
PATCH /api/transactions/TXN-1001/status
{
  "status": "COMPLETED"
}
```

All errors share one shape:

```json
{
  "timestamp": "...",
  "status": 404,
  "error": "Not Found",
  "messages": ["Transaction not found: TXN-9999"]
}
```

## 6. Testing approach

`TransactionControllerTests` uses `@SpringBootTest` + `MockMvc` to test
through the real HTTP layer against the in-memory H2 database, covering
the four required cases plus three more:

1. Transaction created successfully.
2. Transaction rejected for failing validation (negative amount).
3. Duplicate transaction ID rejected.
4. Request for a non-existent transaction returns 404.
5. Valid status update succeeds.
6. Status update rejected once a transaction is in a terminal state.
7. Customer transaction lookup returns only that customer's transactions.

To run:

```bash
./mvnw clean test
```

## 7. Known limitations

- No authentication/authorization — anyone can hit any endpoint.
- No pagination on the customer-transactions endpoint; fine for an
  exercise, would not scale to a customer with a large transaction
  history.
- No idempotency key support beyond the transaction-ID-uniqueness check
  — a client retrying a failed request with a *new* ID would create a
  second transaction.
- Currency and amount are not validated against each other (e.g. no
  currency-specific decimal precision rules — JPY, for instance, has no
  minor unit — this treats all currencies as 2-decimal).
- Enum validation failures for `currency`/`type` return a generic
  "malformed request" message rather than naming the invalid value and
  the allowed set.

## 8. What I'd improve with more time

- Add an idempotency key header for create, independent of transaction ID.
- Make the permitted currency/type/amount limits configurable
  (`application.yml`) instead of hardcoded, so variants don't require
  recompiling.
- Add pagination and filtering (by status, date range) to the
  customer-transactions endpoint.
- Add a currency-aware amount validator instead of a flat 2-decimal rule.
